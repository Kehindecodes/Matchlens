# X2 · Second language via LexiconEntry

**Tier** T3 · **Est** 1 day, 0.5 lite · **Depends on** A4 · **Phase** 8 Submission

## ⚠️ Honest status: this is the least likely thing in the backlog to land

T3, rung 7 of the cut ladder, and it is the last build day. **The answer in the submission is almost certainly the mechanism rather than the feature** — and that answer is genuinely decent, so make it well rather than building half of it badly.

## What the brief asks, and what already exists

The challenge wants *"clear natural-language outputs that could support global studio and streaming scenarios in multiple languages"* (vi).

What is already true, and is worth stating plainly:

- **`Lens.language` is a field**, ISO 639-1, on every lens. Language is a lens property, not a translation layer bolted on afterwards.
- **`ViewerSession.language` is a field too**, so a viewer carries a language independently of the lens.
- **`LexiconEntry` is modelled** — `term`, `language`, `lens`, `phrasing` — keyed by lens, so register survives translation. "Pressing harder" in the analyst register and in the supporter register are different phrasings of one term, and the entity already knows that.

So the design decision is made and the data model carries it. One language ships.

## If it is built — the lite version only

- A second language for the **casual** lens only, since it has the smallest vocabulary.
- Populate `LexiconEntry` for the terms L3's templates actually use. Nothing speculative.
- Switch by `Lens.language`, so adding a language stays a data change (invariant 10).
- **Not machine translation at render time.** That would put a model on the path for every card and break the determinism L3 rests on.

## Acceptance criteria

- [ ] The casual lens renders in a second language, selected by `Lens.language`
- [ ] Adding a term is inserting a `LexiconEntry` row, with no code change
- [ ] Register survives: the same term in two lenses gives two phrasings
- [ ] No model call at render time
- [ ] The first language is unchanged — assert the existing output is byte-identical

## If it is not built

Say this in X3, and it is a real answer rather than an excuse: *language is a lens field and a session field, `LexiconEntry` keys phrasing by lens so register survives translation, and one language ships.* The brief asks whether the design **could** support multiple languages. It can, and the model shows how.

## Do not

- Do not translate with a model at render time.
- Do not ship a half-populated lexicon. A card falling back to English mid-sentence is worse than one language.
- Do not claim multi-language support in the pitch if only the mechanism exists.
