## What to build

- **Container image.** One image, two entrypoints (`apps/pipeline.py`, `apps/delivery.py`), selected by env var or command. Separate images would be smaller — delivery needs none of NumPy or the Agent Framework — but one image means one build, guaranteed version lockstep between the halves, and half the workflow to maintain. For 17 days solo that is the right trade.
- **Azure Container Registry.**
- **Two Container Apps** from that image. **Scale to zero during the build** — a min-1 replica would blow the free grant roughly sevenfold.
- **Service Bus** namespace and queue between pipeline and delivery. The most legible evidence of an event-driven architecture, and visible in the portal.
- **Bicep** — one file, ~150 lines: resource group, registry, environment, two apps, Service Bus, database, Application Insights, storage. The payoff is a repo where `az deployment group create` stands up the whole system.
- **GitHub Actions**, one workflow, one environment, no staging and no approval gates:
  - every push and PR: pinned install, `ruff` lint and format check, type check, `pytest`
  - merge to `main`: build one image, push to ACR, deploy both apps
- **OIDC federated credentials, not a stored secret.** No long-lived credential to leak, and it reads as quality practice to a judge reading the repo. Application secrets come from Container Apps secrets; CI holds only the deploy identity.
- **A budget alert in Cost Management.** Do this first, before any resource exists.

## Acceptance criteria

## Definition of done

Criteria pass, green, status updated.

## Do not

- **Do not use AKS.** It is named in the prize description and is still the wrong choice: it costs money, eats days, and Container Apps demonstrates the same thing.
- Do not use Event Hubs instead of Service Bus (D9).
- Do not add staging, approval gates, release tagging or automated rollback. Container Apps revisions already give you rollback.
- Do not set min-1 replicas yet. That is X4, for the judging window only.
