# A3 · Verifier: six checks, value recomputation, fails closed

**Tier** T1 · **Est** 2 days · **Depends on** A2 · **Phase** 6 Agents
**📝 Walkthrough required** (D29) — `docs/walkthroughs/A3.md`. The second of the two deepest.

## Goal

Every claim gets a `Verification` with all six checks run, a verdict that follows them, and a reason when it fails.

## The model already enforces the shape — you fill in the judgement

`Verification`'s validators do more work than most: `_all_six_checks_ran` refuses a record missing any `CheckName`, `_verdict_follows_the_checks` refuses a pass with a failed check, and `_a_failure_has_a_reason` refuses a fail without one. `CheckResult` refuses a failure with no reason.

So you cannot ship a verifier that quietly skips a check — the row will not construct. What is left is the logic of the six, and `verification/verify()` currently records all of them as `NOT_APPLICABLE` with the reason *"stub: A3 implements this check"*, which is honest rather than a false pass.

## The six

| Check | What it does | Notes |
|---|---|---|
| `citation` | every `evidence_ids` ref resolves to a real row | `Operand.evidence_ids` has `min_length=1`, so emptiness cannot happen |
| `temporal` | nothing cited is from after the moment's clock | **inclusive** at the boundary — A1 settles the wording |
| `entity` | the subject was on the pitch across the window | `NOT_APPLICABLE` for a team subject — that is what the status exists for |
| `value` | **recompute from the record**, independently, and compare | `recomputed_value` is a tuple: one per operand |
| `entailment` | each operand's evidence resolves to rows matching that operand's `subject` and `metric` (**D21** — one rule, arity varies) | |
| `coverage` | every trigger reading and event of the moment appears in some claim's evidence (**D22** — claim-side completeness) | |

**`value` versus `entailment` is the line to hold** (D21): `value` recomputes *from the record*, ignoring what was cited, and catches *the number is wrong*. `entailment` checks *the claim's own evidence* supports it, and catches *the number is right but the citations have nothing to do with it*. Fold them together and you have five checks wearing six names.

D30 is what makes `value` possible at all: all eight metrics are recountable from cited rows.

## ⚠️ It verifies L7's claims too, not only A2's

This is the property worth protecting. The rule-based claims go through the same verifier, so **verifiability is not an agent-only feature** — if the agents are cut, the checks still run against the deterministic claims and the central product claim survives. Build it against L7's output first; A2's claims are then the second case, not the only one.

## What to build

- Real `verify(claim, record)` in `matchlens/verification/`.
- **Fails closed.** The docstring already says a claim without a `Verification` counts as failed; keep that true under timeout, exception and malformed input.
- Verdicts and reasons **persist as data**, because P3 shows rejected claims with their reasons — the clearest multi-agent evidence in the build.
- `latency_ms` is wall time from the span, as the stub already does. Live play has a budget.
- `model` and `model_version` on the verification (invariant 7).

## Acceptance criteria

- [ ] All six checks run on every claim; a record missing one cannot be constructed (the validator proves it — assert the validator fires)
- [ ] **A wrong number fails `value`**, with the recomputed figure in `recomputed_value` and a readable reason
- [ ] **A right number with unrelated citations fails `entailment` and passes `value`.** This single test is what proves the two checks are different
- [ ] A claim citing an event after the clock fails `temporal`; one citing an event exactly at the clock passes
- [ ] `entity` is `NOT_APPLICABLE` for a team subject and genuinely checked for a player subject (D30 allows a named scorer)
- [ ] A moment whose trigger reading appears in no claim's evidence fails `coverage`
- [ ] **Fails closed:** a timeout, an exception or an unparseable claim yields `FAIL` with a reason, never a pass and never no record
- [ ] It runs against **L7's** claims, not just A2's, and they pass
- [ ] `latency_ms` is recorded and the suite stays inside the live budget

## Definition of done

Criteria pass, green, status updated, and `docs/walkthroughs/A3.md` written — the `value`/`entailment` boundary, what fails-closed cost, and which check caught the most real bugs.

## Do not

- Do not let a check return `NOT_APPLICABLE` to avoid implementing it. The stub does that deliberately and visibly; shipping it would be a false pass.
- Do not soften a claim to make it pass. Verification fails claims; it does not edit them.
- Do not recompute `value` from the cited evidence — that is `entailment`. Recompute from the record.
