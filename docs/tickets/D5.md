# D5 · OverlayPacket endpoint

**Tier** T2 · **Est** 0.5 day · **Depends on** L3 · **Phase** 5 Delivery

## ⚠️ This answers a sentence in the challenge brief almost word for word

The brief asks for output:

> *"timed and machine-readable enough to be rendered as synchronized graphical overlays on a live match feed, in the way the platform's rendering partner handles overlays in the production path."*

`OverlayPacket` already **is** that, in the data model: `display_at_clock`, `duration_ms`, `template`, `payload`. The entity is modelled and the enum exists. All that is missing is an endpoint serving them.

**But build it for the streaming path, not a broadcast gallery (D34).** This is the machine-readable form of a card so that a **player renders it over the picture, client-side, per session** — which is what keeps it personalized. A broadcast graphics system renders one overlay for everyone on the feed, and per-viewer insight collapses.

That is the stronger claim anyway. Sofascore's insights are a tab you navigate to; FotMob's are prose you read instead of watching. An insight **on** the picture that differs per viewer is unoccupied, and this endpoint is the only artifact in the build that shows the output is in a form that could do it.

Half a day, T2. **Worth considering promoting to T1** — tier changes are Kehinde's call.

## Goal

An endpoint serving renditions as machine-readable, timed overlay packets a graphics system could consume.

## What to build

- An endpoint returning `OverlayPacket`s for a match, or streaming them on the same release discipline as cards.
- `OverlayPacket` is written by **Rendering**, per the single-writer table. Build it there and serve it from Delivery; do not let Delivery mint one.
- `display_at_clock` is **match clock, never wall clock** — the model's own comment says so, and it is the field that makes the packet synchronisable.
- `duration_ms` must be greater than zero (the model enforces it): how long the overlay stays up.
- `template` is one of `lower_third`, `stat_bar`, `team_card`. Map rendition shape to template; do not invent a fourth.
- `payload` is a flat dict of strings and numbers — the graphics system's fields, not MatchLens's internals. **No ids, no importance scores, no reasons.**
- One packet per rendition, suppressed renditions excluded: there is nothing to render.

## Acceptance criteria

- [ ] Packets are valid `OverlayPacket`s with a positive `duration_ms` and a `display_at_clock` in match clock
- [ ] A suppressed rendition produces **no** packet
- [ ] The payload is flat and contains nothing internal — assert no key holds an id, a score or a reason
- [ ] Each packet maps to exactly one rendition, and `rendition_id` resolves
- [ ] Packets for the same match come out in `display_at_clock` order
- [ ] `template` is always one of the three enum values
- [ ] The output is parseable by something that is not MatchLens — a test that reads it with a plain JSON parser and checks the fields a renderer would need, with no project imports

## Definition of done

Criteria pass, green, status updated. **Capture one packet as a JSON sample for the submission** — a judge reading the brief's overlay sentence will want to see exactly this, and a four-line JSON blob is more convincing than a paragraph.

## Do not

- Do not render pixels. This is a data contract for someone else's renderer.
- Do not put internal fields in the payload.
- Do not use wall clock.
- Do not emit packets for suppressed renditions, and do not substitute an empty one.
