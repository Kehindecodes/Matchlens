# L1 · Lens entity and three presets as config rows

**Tier** T1 · **Est** 0.5 day · **Depends on** F1 · **Phase** 4 Lenses ⭐

## Goal

The three shipping presets exist as **data**: `match`×`casual`, `match`×`analyst`, `team`×`engaged`. `matchlens/lenses/__init__.py` currently holds one hardcoded `Lens` — the stub says so.

## The real work here is not the rows, it is their numbers

`importance_threshold` is what makes the casual lens sit silent while the analyst fires on the same moment. That silence is the demo. So L1 is a **calibration** ticket wearing a config ticket's clothes, and it cannot be done in the abstract.

**M1b is done, so the importance distribution exists.** Run the demo match, look at the histogram, and set the thresholds against it:

- **casual** — high enough to drop the majority of moments. If casual shows every moment the analyst does, there is nothing to demonstrate
- **analyst** — low, near the floor
- **engaged** — between them, and note that under D2 team scope *reweights* importance before the threshold applies, so its effective cut is not comparable to the match lenses' on raw numbers

Pick the numbers from data, and say in the commit what distribution they were picked against. The next recalibration of M1b moves this ground.

## What to build

- Replace `_LENSES` with the three presets, loaded from **committed data, not a Python literal**. `understanding/signal_priors.json` is the precedent — a JSON file beside the registry, read at startup.
- Keep `get(lens_id)` and `all_lenses()` as they are. Only the source of the rows changes.
- The `Lens` validator already enforces `focus_team` required iff scope is `team`, so `team_engaged` must name a side — the demo match's home team.
- `breakthrough_types` is **goals only**, and per the data model it is load-bearing only for `player` scope. Set it, do not lean on it.
- `allowed_claim_types` differs per depth — the casual lens drops comparative claims carrying raw numbers.

## Acceptance criteria

- [ ] Three lenses, `get()` and `all_lenses()` returning them, every field populated from data
- [ ] **Invariant 10 has a test:** no lens id appears as a string literal anywhere in `matchlens/` outside the config file. Walk the tree, same shape as `test_nothing_outside_config_reads_os_environ`. A hardcoded `if lens_id == "match_casual"` is the failure this catches
- [ ] Adding a fourth lens is editing the data file only — prove it in a test by loading a four-lens fixture and asserting nothing in code needed changing
- [ ] `team_engaged` names a `focus_team`; both match lenses leave it null. The validator covers this, so assert it is actually exercised
- [ ] **The thresholds separate:** on the demo match, the count of moments clearing casual's threshold is materially lower than analyst's. Assert the ordering, not a magic number
- [ ] `focus_player` is null on all three (player scope deferred, D1)

## Definition of done

Criteria pass, `ruff` and `pytest` green, status updated. Record in the commit which importance distribution the thresholds were set against.

## Do not

- Do not hardcode a lens name in any component. L2 and L3 read `Lens` fields, never lens identities.
- Do not add a fourth lens. Three presets, two axes, by D1.
- Do not put the rows in a database. One container, no DB on the path in v1 (D23); committed JSON is the honest shape.
