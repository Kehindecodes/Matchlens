# R1 · SignalPrior from a generated sample

**Tier** T1 · **Est** 1 day, **0.25 as lite** · **Depends on** U3 · **Phase** Reference data — offline, runs in parallel

## Goal

For each v1 signal, a mean and standard deviation over a sample of generated matches, stamped with the generator version that produced it.

**Take the lite version: 20 matches, not 200.** That is rung 2 of the cut ladder, marked free, and it is enough to stop the cold-start flood — which is the only job this ticket has.

## Why it exists

It solves one problem, stated in the data model: at four minutes there is no match baseline, and a z-score against five minutes of data is noise — *"exactly when a naive system floods the viewer with 'unusual!' moments."* D11's shrinkage blend needs something to blend towards, and this is it. Under D15 the same cold start recurs after every goal, so the prior earns its keep several times a match rather than only at kickoff.

## ⚠️ Ask before starting

**The listed dependency is U3, but this also needs R2.** A prior built only on `COMEBACK` is a prior *of* the comeback archetype — `z_prior` would then mean "unlike the demo match" rather than "unusual". Sampling across all four archetypes is what makes the number mean anything, so R1 should depend on **U3 and R2**. Raised rather than assumed, since changing a dependency is a plan change.

## What to build

- An **offline script** — `scripts/build_priors.py` or similar — that is not part of the runtime pipeline. Its output is committed.
- For each of the **four v1 signals** (D24 — no `line_height`): run the sample, collect every reading's `value`, compute `mean` and `stddev`, emit one `SignalPrior` row.
- **Sample across all four archetypes** with a stated, deliberate split. Record it.
- `sample_size` and `generator_version` on every row.
- **A loader that refuses a mismatched prior, loudly.** The data model is explicit: *"a prior is only valid for the generator that made it."* A stale prior silently in use is worse than no prior, because every z_prior in the match is then quietly wrong and nothing looks broken.

## Be honest about what `z_prior` means

The prior comes from synthetic matches, so `z_prior` measures **"unusual for this generator"**, not "unusual for football". That is fine — it is the right number for the job and the cold-start problem is real either way — but it must not be described as anything else.

In the pitch, `z_match` is "something changed in this match" and survives contact with a judge. `z_prior` is "this match is unusual **for our simulated population**". With real data behind it, it would become "unusual for this competition". State the distinction before someone finds it: the mechanism is right and the reference population is synthetic, and those are two separate claims.

The deeper circularity is worth naming in the same breath. U4 uses `z_prior` to help decide what is notable; the prior comes from the generator; the generator is parameterised by archetypes written by hand. So "notable" is, at the bottom, relative to parameters we chose. **P4 is the mitigation** — a signal that only reads well on one archetype gets caught there — which is another reason R2 comes first.

## Acceptance criteria

- [ ] **Four** `SignalPrior` rows, one per v1 signal. Not five — `line_height` is deferred (D24)
- [ ] `sample_size` and `generator_version` present on every row
- [ ] The sample spans all four archetypes, and a test asserts it is **not** single-archetype
- [ ] `stddev > 0` for every signal. A constant signal makes `z_prior` a division by zero, and it also means the signal is measuring nothing
- [ ] The loader **refuses** a prior whose `generator_version` differs from the running generator, with a clear error. A test covers the refusal, not just the happy path
- [ ] Deterministic: the same sample seeds produce byte-identical priors
- [ ] **Evidence that 20 is enough:** re-running on 40 matches moves each mean by less than a stated tolerance. This is what justifies taking the lite cut rather than assuming it

## Definition of done

Criteria pass, green, status updated. Commit the generated priors and the seed list that produced them, so the numbers are reproducible rather than just present.

## Do not

- Do not run this inside the pipeline. It is offline, and its output is data.
- Do not build a prior for `line_height` (D24).
- Do not describe `z_prior` as "unusual for the Premier League" anywhere — in code, UI, README or pitch.
- Do not sample only the demo archetype, even if R2 is not finished. If R2 is absent, say so and stop rather than building a prior that silently means something narrower than its name.
