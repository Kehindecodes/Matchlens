# U2 · ShotValue hand-calibrated lookup

**Tier** T1 · **Est** 0.5 day · **Depends on** S2 · **Phase** 2 Understanding

## Goal

Every shot carries a 0–1 value, with the distance and angle it was derived from kept on the row.

## What to build

- `matchlens/understanding/shot_value.py`
- `value(event, match) -> ShotValue` for every `Action.SHOT` and `Action.PENALTY`.
- `distance` and `angle` computed from the event position and the attacking goal. **Normalise the coordinates first** using `Team.attack_direction_by_period` — a second-half shot has mirrored coordinates, and an un-normalised distance makes every second-half shot wrong in the same direction, which is hard to spot by eye.
- A **hand-calibrated lookup** over distance and angle: a small table with interpolation, or a simple closed form. Not a fitted model.
- `model_version` as a module constant, bumped by hand whenever the table changes. The row stores it so an old value stays explainable after a recalibration.

## The plausibility bar

It does not need to be accurate. It needs to be **defensible from the two inputs on the row**, because that is the whole reason the inputs are stored:

- a penalty returns a fixed constant, not the lookup
- a tap-in is high, a 30-yard shot is low
- at the same distance, a tight angle is worth less than a central one
- monotonic in both inputs, with no local bumps

## Acceptance criteria

- [ ] Every shot in a generated match has exactly one `ShotValue`; no shot is missing one and none is valued twice
- [ ] All values in `[0, 1]` — the model's `UnitInterval` enforces it, so a test feeding extreme coordinates must not raise
- [ ] Monotonically non-increasing as distance grows at fixed angle, and as the angle narrows at fixed distance. Assert over a grid, not two examples
- [ ] A penalty event returns the penalty constant
- [ ] Pure function: same event, same value, no RNG anywhere in the module
- [ ] Second-half shots are normalised — a test mirrors a first-half shot into the second half and asserts the same value
- [ ] `model_version` is asserted in a test, so changing the table without bumping it fails

## Definition of done

Criteria pass, green, status updated.

## Do not

- **Never call this xG** (invariant 12). `shot_quality` in code, in the UI, in comments, in commit messages. It is a hand-calibrated lookup over invented data and calling it xG is a claim we cannot defend.
- Do not fit anything. If a value cannot be explained from the distance and angle on the row, the lookup is too clever.
- Do not read frames.
- Do not aggregate. Summing shot values over a window is `chance_quality`, which is U3.
