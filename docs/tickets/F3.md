# F3 · Seeded match simulator

**Tier** T1 · **Est** 2 days · **Depends on** F2 · **Phase** 0 Foundation
**Stories** V2 ("no statement contradicts what happened"), J1

## Goal

A deterministic simulator that produces one plausible football match from a seed: positional frames and ~1,800 events, with correct phase tagging.

## Why this is the single most important ticket

**This is the foundation, not the database schema.** Working the dependency graph backward, every chain bottoms out here. Because the data source is synthetic, a non-deterministic or implausible generator makes every downstream test unreliable and calibrates every signal against noise.

Everything after Phase 0 waits on this. It should start no later than **10 October**.

## ⚠️ Ask before starting

**The frame rate is unresolved — see D13 in `docs/DECISIONS.md`.** The proposal is 2 Hz rather than 10 Hz, now that player scope is deferred and run detection is not built. Do not pick one. Ask Kehinde, and make it `settings.frame_rate_hz` either way.

The difference is not trivial: at 10 Hz you need smooth plausible motion for 22 players; at 2 Hz you need formation positions that drift sensibly, which is a much smaller job.

## What to build

- `matchlens/source/simulator.py` — takes a seed and an archetype, yields frames and events.
- Seed every random draw from one seeded `numpy.random.Generator` passed down explicitly. **No module-level RNG, no `random` module, no implicit global state.** This is what determinism rests on.
- A match clock as a variable from the first line. **Never wall time.** Playback speed (F4, D3) is trivial if the clock is a variable and painful to retrofit if it is not.
- Two teams, formations, named fictional players, substitutions.
- Events: pass, carry, shot, tackle, interception, clearance, foul, throw_in. Roughly one every 3–4 seconds of play, ~1,800 per match.
- **The match events too (D16):** `substitution` (with `player_on`), `red_card`, `yellow_card`, `period_start`, `period_end`. Nothing downstream works without them — the derived roster, epoch detection, and `Match.period_boundaries` all read these. Include at least one double substitution at a single clock, and at least one archetype with a red card.
- **Every action, not just interesting ones.** Selection happens later. If the log only held interesting events the verifier could never recompute a count, because the boring events making up the denominator were never written.
- Frames at `settings.frame_rate_hz` with ball position and all 22 player positions.
- Phase tagging: `in_play`, `stopped`, `set_piece`. **Signals must be able to exclude stopped time** or possession percentages are wrong.
- `under_pressure` set on events by the generator, from positions at execution.
- `frame_ref` on each event, aligning it to the nearest frame.
- Goals, and at least one archetype that produces an equaliser against the run of play — that shape is what the demo narrative needs.

## Plausibility bar

It does not need to be a good football model. It needs to be good enough that the five signals read sensibly:

- Possession alternates in sequences, not alternate events
- Territory shifts over multi-minute spells rather than randomly per event
- A defensive line has a coherent height that can move
- Shots cluster where chances come from, not uniformly
- Pressing has an intensity that can change

If a signal can be satisfied by a coin flip, the generator is too random to calibrate against.

## Acceptance criteria

- [ ] The same seed produces a **byte-identical** match twice. Test by serialising both runs and comparing.
- [ ] Two different seeds produce visibly different matches
- [ ] ~1,800 events per match, one every 3–4 seconds of in-play time
- [ ] Frames emitted at exactly `settings.frame_rate_hz`
- [ ] `seq` is monotonic across the combined frame and event stream
- [ ] Phase tagging present, and total `in_play` time is plausible (roughly 55–65 minutes of a 90-minute match)
- [ ] Every event has a `frame_ref` pointing at a frame within half a frame interval
- [ ] Possession sequences average more than one pass — a test asserting mean sequence length > 2 catches the "random per event" failure
- [ ] At least one archetype produces a goal against the run of play
- [ ] `substitution`, `red_card`, `period_start` and `period_end` events are emitted, and a derived `was_on_pitch` agrees with the roster across a double substitution and a sending-off
- [ ] The roster is emitted as a pre-match setup message, before the first frame or event

## Definition of done

Criteria pass, `ruff` and `pytest` green, status updated. Commit the seed used for the demo match in `settings` so the video and the tests run on the same data.

## Do not

- Do not emit `Run`s. Player scope is deferred, and when it lands runs are **derived** from frames, not emitted (D12).
- Do not emit signal readings or anything judging what is interesting. That is Phase 2 and 3. The generator declaring what matters is the circularity this design exists to avoid.
- Do not persist to a database. Yield in memory; Ingest handles intake (S2).
- Do not build the other three archetypes here. That is R2.
