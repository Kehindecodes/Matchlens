## ⚠️ The title contradicts the code, and the code has already chosen

This ticket is called *"events **strictly** before clock X"*, and `ARCHITECTURE.md` says the same. But `explanation.explain()` filters with `clock_ms <= clock` — **inclusive** — and has done since L7.

Inclusive is almost certainly right: a goal moment must be able to cite its own goal event, and A3's temporal check is specified as *"nothing cited from after the clock"*, which permits an event **at** it. So the code is correct and the title is stale. This is the leftover from **Q6**, which assigned the choice here.

**Settle it, say which, and fix the title** — in this brief, the backlog row and `ARCHITECTURE.md`. Do not leave two words in the repo meaning different things about the one boundary the explainer is not allowed to cross.

## Goal

Make invariant 6 **structural** rather than defensive.

## Why it is still worth half a day now that `explain()` filters

Today `explain()` re-filters whatever the caller hands it, and the docstring says so: *"Nothing after `moment.clock_ms` is read, whatever the caller passes."* That is correct and it is a **convention** — a list comprehension one edit away from being removed by someone tidying up.

Invariant 6 asks for more: *"It must be structurally impossible for it to reason from the future."* That means the reader cannot return the future, so the explainer cannot see it even when its caller is wrong. The filter moves from the consumer to the data access layer, which is where the invariant says the boundary lives.

The same reasoning as `RecordReader`, which holds no frame reference *so there is nothing on it to follow to a `Frame`* (invariant 1). A1 is that pattern applied to time.

## What to build

- A reader that takes a clock and serves only the record at or before it — events, readings, epochs. Nothing later exists from its point of view.
- `RecordReader.events_between` already returns a tuple, so a later append cannot change what a reader holds (`test_a_range_is_a_snapshot`). Build on that rather than beside it.
- No frame reference anywhere on it (invariant 1).
- Then **delete the defensive filters in `explain()`**, because leaving both means two places own one rule and the weaker one will be trusted.

## Acceptance criteria

- [ ] **V2: the explainer cannot see the future.** The weak version asks the reader for everything and asserts nothing later comes back. The strong version is the one that matters: hand `explain()` a **deliberately poisoned** log containing events after the moment's clock and assert the claims are byte-identical. That proves the structure, not the filter
- [ ] Inclusive at the boundary: an event exactly at `moment.clock_ms` is visible and citable
- [ ] A reader is a snapshot — appending after it was taken does not change what it returns
- [ ] No attribute path from the reader reaches a `Frame`; a test walks the object, it is not a comment
- [ ] The defensive filters in `explain()` are gone, and the poisoned-log test still passes
- [ ] The title, the backlog row and `ARCHITECTURE.md` all say the same thing about inclusive versus strict

## Definition of done

Criteria pass, green, status updated, and `docs/walkthroughs/A1.md` written — covering why enforcement moved layers, and what the poisoned-log test proves that the filter did not.

## Do not

- Do not keep both the filter and the reader. Pick the structural one.
- Do not expose a clock parameter a caller can set to the future "for testing". That is the hole this closes.
