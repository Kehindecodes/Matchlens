# U3 · Four signal functions

**Tier** T1 · **Est** 1.5 days · **Depends on** U1, U2 · **Phase** 2 Understanding

## Goal

One function per v1 `Signal`, each computing that signal's value for one team over a window, on a rolling cadence.

**Four signals (D24):** `territory`, `possession_control`, `pressing_intensity`, `chance_quality`. All event-derived. **`line_height` is deferred** — it stays in the `Signal` enum, as `RefKind.RUN` does, and is not built here.

## What this ticket does not do

The one-liner used to say "emitting SignalReading", and this ticket cannot. `SignalReading` is frozen with `baseline`, `z_match` and `z_prior` required, and those are **U4, which is 🧑 reserved**. So U3 produces values, `n` and `confidence`; U4 assembles the row. Building complete readings here would either write U4 or invert the dependency.

## ⚠️ Read this before writing the window code

The two read APIs use **opposite interval conventions**:

| API | Interval |
|---|---|
| `RecordReader.events_between(from, to)` | **`[from, to)`** — inclusive start, exclusive end |
| `FrameAccess.frame_window(clock_ms, span_ms)` | **`(clock − span, clock]`** — exclusive start, inclusive end |

With line height deferred this ticket only reads events, so the trap is dormant — **but do not assume one convention is "the" convention.** Write the window helper so the interval is explicit at the call site, because line height reinstates the frame read later and the clash comes back with it. The failure mode is quiet: slightly wrong shares at every window edge, nothing crashing.

## What to build

`matchlens/understanding/signals.py`, one function per signal, all with the same signature, returning the value in the signal's own units with those units in the docstring:

- **`territory`** — share of in-play possession time or events in the opponent's third, from U1's `start_zone` / `end_zone`
- **`possession_control`** — possession share over the window, from U1's records
- **`pressing_intensity`** — PPDA: opponent passes per defensive action in the opponent's own two-thirds. Call it `pressing_intensity` in every user-facing string, never PPDA
- **`chance_quality`** — U2's shot values aggregated over the window

Also:

- **`n` and `confidence`.** The window's sample count, and a confidence that falls as `n` falls. Thin windows must be visibly thin — this is what stops a two-event window reading as a tactical shift.
- The **rolling cadence** — how often a reading is produced. One decision, in config, not per signal.
- The **clamped window** (D15): `window_start = max(clock − settings.signal_window_ms, epoch.start_clock_ms)`. The effective width is what U4 puts on the reading as `window_ms`, which is why that field exists.
- `calltrace.entered("Understanding")`.

## Acceptance criteria

- [x] One function per v1 signal, identical signatures, units documented. **No `line_height`**
- [x] **Stopped time is excluded.** A test over a window containing a long stoppage gets the same answer as the in-play-only computation
- [x] The window helper makes its interval explicit, with a test on the boundary case — one event exactly on each edge, counted deliberately
- [x] `confidence` is materially lower on a 2-event window than on a full one. Assert the direction, not a magnitude
- [x] The clamped width is returned alongside the value, so U4 has it without recomputing
- [x] Deterministic on a fixed seed
- [ ] Each signal reads sensibly on at least two archetypes — a signal a coin flip could satisfy is not calibrated. R2 provides them; if only one archetype exists, say so rather than asserting against one match
- [x] `pressing_intensity` dissociates from `possession_control` on at least one archetype. **This is the criterion that matters most** — it is the evidence for D10's orthogonal-basis claim, and it is why this signal survived the cut. If the two move together on every match, either the generator or the signal is wrong

## Definition of done

Criteria pass, `ruff` and `pytest` green, status updated. Note in `docs/QUESTIONS.md` anything the calibration forced you to assume.

## Do not

- Do not build `line_height`, and do not remove it from the `Signal` enum. Deferred, not cancelled (D24).
- Do not compute baselines, `z_match` or `z_prior`. **U4 is 🧑 reserved** — leave them absent and say so.
- Do not read the frame window. Nothing in v1 does, and a read here would be the only one.
- Do not decide what is interesting. No thresholds, no importance, no cooldown — that is M1.
- Do not call `chance_quality` xG anywhere.
- Do not add a fifth signal. D10 says these are an orthogonal basis, not a bag of detectors.
