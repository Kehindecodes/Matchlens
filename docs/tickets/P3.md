# P3 · Rejected-claims view with reasons

**Tier** T2 · **Est** 0.5 day · **Depends on** A3, P1 · **Phase** 7 Producer

## ⚠️ Build this one first, ahead of the rest of Phase 7

A3 is done, which unblocks it — and the backlog's own note is the reason: *"the clearest multi-agent evidence in the build — one agent visibly overruling another."*

Everything else in the submission **asserts** that claims are checked. This is the only place a stranger **sees** it happen. Half a day, and it converts the multi-agent claim from a sentence in the README into something a judge can click.

**Its dependency on P1 is probably avoidable — ask.** A standalone page listing a match's verifications is far cheaper than the full producer view, and P1 is a day. If P3 has to wait for P1 it becomes 1.5 days and will not land.

## Goal

For a match, every claim with its verdict: accepted ones and rejected ones, each rejection showing **which check failed and why**.

## The data is already shaped for it

`Verification.checks` is a `dict[CheckName, CheckResult]`, and `CheckResult` refuses a `FAILED` status without a `reason` — the validator guarantees every rejection can explain itself. `_all_six_checks_ran` guarantees none is missing. So this view has nothing to compute; it displays what A3 already had to record.

## What to build

- A page listing a match's claims with verdict, and per claim the six checks with status and reason.
- **Distinguish `NOT_APPLICABLE` from `PASSED`.** Six green ticks when one check was N/A — `entity` on a team subject, which is exactly what that status exists for — overstates what was verified. A judge who notices that notices it loudly.
- Show the claim's metric, value and `recomputed_value` side by side on a `value` failure. "Claimed 8, recomputed 7" is the most convincing single line in the build.
- Plain HTML and JS, no framework.

## Acceptance criteria

- [x] Accepted and rejected claims both listed; rejections are not hidden
  - `test_accepted_and_rejected_claims_are_both_listed`; the page defaults to all, and "Show rejected claims only" is the producer's own filter
- [x] Each rejection names the failed check and shows its reason verbatim from the record
  - `test_a_rejection_names_each_failed_check_and_carries_its_reason_verbatim`, `test_a_rejection_arrives_with_its_failed_check_and_the_reason_verbatim`
- [x] `NOT_APPLICABLE` renders differently from `PASSED` — never as a tick
  - `test_a_check_that_did_not_apply_is_carried_as_such_and_never_as_passed`, `test_a_check_that_did_not_apply_is_drawn_differently_from_a_pass`
- [x] A `value` failure shows claimed against recomputed
  - `test_a_value_failure_shows_what_was_claimed_beside_what_was_recomputed`
- [x] The view computes nothing: no recomputation in the browser, so it cannot agree with itself while the pipeline is wrong
  - `test_the_view_recomputes_and_rechecks_nothing` (the verifier and every check are made to raise), `test_the_script_only_displays_what_the_server_sent`
- [x] It works on a match where **nothing** was rejected, without implying the checks did not run
  - `test_a_match_where_nothing_was_rejected_shows_every_claim_and_every_check`; the summary then reads "N claims, each put through all six checks. None was rejected."
- [x] No new dependency

## Definition of done

Criteria pass, green, status updated. **Screenshot one rejection for the submission** — a claim killed by its own verifier, with the reason, is the evidence for the multi-agent flow and for "nothing it says is unverifiable" in the same image.

## Do not

- Do not let a viewer reach this page. It is a producer surface.
- Do not recompute a value in the browser.
- Do not soften or summarise a failure reason. The verbatim reason is the point.

## As built (Q45: 1B, 2A)

- **Audit is real (1B).** `matchlens/audit/__init__.py`: `Audit` keeps one `Audited` entry per moment (the moment, its claims, a verdict for each, a rendition for each lens), in memory, append-only. A moment is recorded once (`AlreadyRecorded`), and a claim with no verdict is refused (`Unverified`), so the trail cannot lose a rejection by omission. It is built in `apps/delivery.py` and handed to the `Pipeline` and to `create_app`, as `Mutes` and `Ladder` are. `audit.record` is now `Audit.record`. v1 has no database (D38); a durable one goes behind the same interface. This settles O4 as in-process, which is yours to move into DECISIONS.
- **The card path only (2A).** The pipeline records the claims `_editorial` verifies. A model's answer asked for only to be scored, because the model is already down the ladder, is not in the trail (`test_an_answer_asked_for_only_to_be_scored_is_not_in_the_trail`).
- **The view.** `matchlens/audit/claims.py`: `claims_page(audit, after)` words every figure and clock on the server, so the browser prints and computes nothing. `GET /producer/claims/data?after=N` returns the moments after the N-th and the totals over the whole trail; `GET /producer/claims` is the page. Both exist only with the producer view (Q43: 4B), and `claims.html`, `claims.js` and `claims.css` are 404 without it.
- **The page.** `web/claims.html`, `claims.js`, `claims.css`, linked from the producer page and from no viewer page. Newest moment first; polls every 2 s from the cursor; a restarted match clears and starts over. Each claim lists all six checks in the order they run, with the mark `✓`, `✕` or `–`, the status in words, and A3's reason verbatim. A claim shows who proposed it and who checked it (invariant 7).
- **Raw values.** It prints the record as it is, on the same footing as A6's drawer (Q42: 1A). Reasons keep their ids (`m-1-home's chances over 3925570–4091035 ms is 1 in the record, not 3`), since a reason is quoted word for word.
- **Seen live.** Seed 1 at 25× with the demo cache and no live model: 52 moments, 186 claims, 3 rejected, which are the three A3 rejections in `docs/evidence/A2-cache-seed1.txt`. Screenshot: `docs/screenshots/P3-rejected-claim.jpg` (gpt-5.4-mini's claim of 3 chances, A3's recount of 1).
- **Not done here.** The trail is lost on a restart, like sessions and mutes. A claim A2 proposed that fails the schema gate is dropped at source (invariant 5) and has no `Verification`, so it is in no view.
