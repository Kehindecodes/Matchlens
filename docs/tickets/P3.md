# P3 · Rejected-claims view with reasons

**Tier** T2 · **Est** 0.5 day · **Depends on** A3, P1 · **Phase** 7 Producer

## ⚠️ Build this one first, ahead of the rest of Phase 7

A3 is done, which unblocks it — and the backlog's own note is the reason: *"the clearest multi-agent evidence in the build — one agent visibly overruling another."*

Everything else in the submission **asserts** that claims are checked. This is the only place a stranger **sees** it happen. Half a day, and it converts the multi-agent claim from a sentence in the README into something a judge can click.

**Its dependency on P1 is probably avoidable — ask.** A standalone page listing a match's verifications is far cheaper than the full producer view, and P1 is a day. If P3 has to wait for P1 it becomes 1.5 days and will not land.

## Goal

For a match, every claim with its verdict: accepted ones and rejected ones, each rejection showing **which check failed and why**.

## The data is already shaped for it

`Verification.checks` is a `dict[CheckName, CheckResult]`, and `CheckResult` refuses a `FAILED` status without a `reason` — the validator guarantees every rejection can explain itself. `_all_six_checks_ran` guarantees none is missing. So this view has nothing to compute; it displays what A3 already had to record.

## What to build

- A page listing a match's claims with verdict, and per claim the six checks with status and reason.
- **Distinguish `NOT_APPLICABLE` from `PASSED`.** Six green ticks when one check was N/A — `entity` on a team subject, which is exactly what that status exists for — overstates what was verified. A judge who notices that notices it loudly.
- Show the claim's metric, value and `recomputed_value` side by side on a `value` failure. "Claimed 8, recomputed 7" is the most convincing single line in the build.
- Plain HTML and JS, no framework.

## Acceptance criteria

- [ ] Accepted and rejected claims both listed; rejections are not hidden
- [ ] Each rejection names the failed check and shows its reason verbatim from the record
- [ ] `NOT_APPLICABLE` renders differently from `PASSED` — never as a tick
- [ ] A `value` failure shows claimed against recomputed
- [ ] The view computes nothing: no recomputation in the browser, so it cannot agree with itself while the pipeline is wrong
- [ ] It works on a match where **nothing** was rejected, without implying the checks did not run
- [ ] No new dependency

## Definition of done

Criteria pass, green, status updated. **Screenshot one rejection for the submission** — a claim killed by its own verifier, with the reason, is the evidence for the multi-agent flow and for "nothing it says is unverifiable" in the same image.

## Do not

- Do not let a viewer reach this page. It is a producer surface.
- Do not recompute a value in the browser.
- Do not soften or summarise a failure reason. The verbatim reason is the point.
