# Data model

22 entities in five groups. Groups A and B are a faithful record with no editorial judgment in them. Group C is where judgment enters. D is delivery, E is reference data computed once offline.

Types are the intent, not necessarily the Pydantic spelling. Pick sensible Python types; `clock_ms` is always milliseconds from kickoff as an `int`.

> **Relationships and cardinalities live in `docs/RELATIONSHIPS.md`.** Read it alongside this file before modelling anything — several cardinalities there are where an invariant is enforced structurally rather than by a runtime check.

> **The single most important boundary:** agents never read `Frame`. They read `Event`, `Possession`, `SignalReading` and above. Enforce it in the data access layer with a failing test, not by convention.

---

## A · Match record

Generated by the simulator. Append-only, never edited after emission. Answers "what happened", with no view on what mattered.

### Match
The root record everything hangs off, and the thing a demo replays.

| Attribute | Meaning |
|---|---|
| `match_id` | Unique identifier |
| `pitch_length_m`, `pitch_width_m` | Metres, so coordinates can be interpreted |
| `kickoff_at` | Notional start time |
| `period_boundaries` | **Derived** from `period_start` / `period_end` events, not stored pre-match (D16) — added time cannot be known at kickoff, so storing it here meant another mutated field |
| `archetype_id` | Which archetype generated this fixture |
| `seed` | Regenerates a byte-identical match. Tests and the demo video depend on this |

### Team
Almost every signal is per-team, so they need stable identity and a known attacking direction.

| Attribute | Meaning |
|---|---|
| `team_id`, `match_id` | |
| `name`, `short_name` | Display name, and the abbreviated form for overlays |
| `formation` | Starting shape, e.g. `4-3-3` |
| `is_home` | |
| `attack_direction_by_period` | Which way this team attacks each half. **Normalise coordinates at read time, never at write time.** |

### Player

| Attribute | Meaning |
|---|---|
| `player_id`, `team_id` | |
| `shirt`, `name`, `position` | Names are fictional, to avoid real-player trademarks |
| `is_starter` | Whether they started the match. The only time-related thing stored on a player |

⚠️ **`on_clock_ms` and `off_clock_ms` were removed — see D16.** They changed when a player was substituted or sent off, which contradicted the append-only rule and made verification irreproducible. Who was on the pitch at a given clock is **derived** from `is_starter` plus the `substitution` and `red_card` events in the log:

```
enters = is_starter ? 0 : clock of the substitution that brought them on (else never)
leaves = clock of the substitution taking them off, or of their red card, or match end
```

`was_on_pitch(player, clock_ms)` is a function over the frozen event log, **not** a method on this model. It is what the verifier's entity check calls.

### Frame
A positional snapshot of everyone on the pitch. Memory only — never a row per frame in a database.

**Why frames survived the loss of player scope:** positional data is the only source for **defensive line height**, and for block width, compactness and average positions. Events say where the ball-actor was, never where the back four are standing — and those measures carry one of the five signals plus two of the three casual phase explainers.

⚠️ **The rate is an open decision — see D13.** 10 Hz existed for run detection, which needs sub-second resolution. Line height needs 1–2 Hz. It is a generator parameter, not a schema change, so raising it back later costs nothing. **Ask before F3 fixes a value.** Figures on this page assume 2 Hz.

| Attribute | Meaning |
|---|---|
| `seq` | Monotonic. **The ordering key for the whole system.** |
| `clock_ms`, `period` | |
| `phase` | `in_play` \| `stopped` \| `set_piece`. **Signals must exclude stopped time** or possession percentages are wrong |
| `ball_x`, `ball_y`, `ball_z` | Metres. Origin at the centre spot, x along the length, z is height |
| `ball_speed` | m/s |
| `carrier` | Player in possession, or null if loose or in flight |
| `players` | Array of `[player_id, x, y, speed]`. **Positional arrays, not objects** — key names would roughly double the payload |

### Event
Every on-ball action, **plus the match events that change the roster or the clock** (D16). **Not key moments — every action**, roughly 1,800 per match, one every 3–4 seconds of play.

Selection must happen *after* the record is complete. If the log only held interesting events, the verifier could never recompute a count, because the boring events making up the denominator were never written.

| Attribute | Meaning |
|---|---|
| `event_id` | **What claims cite as evidence** |
| `seq` | Aligns the event to the frame stream |
| `clock_ms`, `period` | |
| `action` | See the `Action` enum. On-ball actions plus `substitution`, `red_card`, `yellow_card`, `period_start`, `period_end` — the positional fields are null for those |
| `player`, `team` | |
| `start_x`, `start_y`, `end_x`, `end_y` | Metres. For a shot, where it arrived |
| `outcome` | `complete`, `incomplete`, `blocked`, `goal`, `saved`, … |
| `receiver` | Intended or actual recipient, for passes |
| `player_on` | The player coming on. **Set only for `substitution`**, where `player` is the one coming off. Null for a red card or an injury with no replacement. Explicit pairing rather than two paired events, because a double substitution at one clock would otherwise be ambiguous — and the 58:00 double change is the hinge of the demo narrative |
| `under_pressure` | Whether an opponent was within pressing distance at execution. **Generator-set** |
| `body_part` | Foot, head, other. Feeds shot quality |
| `frame_ref` | The frame this aligns to, so positional context can be recovered |

## B · Derived understanding

Computed from group A by **deterministic code, not by AI**. Running the detectors again on the same match gives identical output. This is what makes verification possible.

### Run — NOT BUILT IN v1
Documented because it is what player scope will need, and because `Lens` carrying scope as data is what makes adding player scope a config row rather than a rebuild. See **D1** and **D12**.

Attributes when it lands: `run_id`, `player`, `team`, `run_type` (`in_behind` | `into_channel` | `overlap` | `dropping_off` | `decoy`), `start_clock_ms`, `end_clock_ms`, `peak_speed`, `distance_m`, `separation_m`, `beat_defender`, `ball_available`, `end_state` (`served` | `unplayed` | `offside`), `concurrent_event`, `frame_refs`.

### Possession
A sequence of consecutive events by one team. Possession control is measured in **sequences, not raw time** — "they can no longer string passes together" is a better story than a percentage.

`possession_id`, `team`, `start_clock_ms`, `end_clock_ms`, `pass_count`, `start_zone`, `end_zone`, `outcome` (`shot` | `turnover` | `foul` | `out_of_play`), `event_ids`.

### SignalReading
A **signal** is a definition (a function). A **reading** is an observation (data). Only readings are stored.

Interpretive claims are accepted by the verifier only if they cite a reading. No reading means the claim is unsupported *by definition*, which turns a philosophical problem into a lookup.

| Attribute | Meaning |
|---|---|
| `reading_id` | Citable as evidence |
| `signal` | `territory` \| `possession_control` \| `pressing_intensity` \| `chance_quality` \| `line_height` |
| `team`, `clock_ms` | |
| `window_ms` | The **effective** window actually covered, not the nominal configured length. **D15** clamps the window start to the epoch start, so shortly after a goal this is much smaller than nominal. Keep the nominal value alongside it if you want it for debugging |
| `value` | The measured number, in the signal's own units |
| `baseline` | What counts as normal here. A value of 14.2 means nothing until you know the match average is 3.1 |
| `z_match` | Deviation from this match's baseline. "Something just changed." Drives live moments |
| `z_prior` | Deviation from the offline prior. "This match is unusual." High `z_prior` with low `z_match` is the signature of a stable oddity, e.g. a consistently scrappy game |
| `trend` | `rising` \| `falling` \| `steady`. Most insight is change, not level |
| `confidence` | Lets a signal declare itself unreliable on a thin sample. Stops PPDA producing nonsense in the opening minutes — and, under **D15**, in the minutes right after a goal or red card, where it falls out of the shortened `window_ms` rather than needing a special case |
| `epoch_id` | Which game state this reading was taken in. **Unambiguous by construction** — D15 means a window never spans two epochs, so this is always the epoch at the reading's clock |

### Epoch
A stretch of match with constant game state. A red card or a goal changes the game, and averaging a baseline across one corrupts it.

`epoch_id`, `match_id`, `start_clock_ms`, `score_state`, `player_counts`, `trigger` (`goal` | `red_card` | `half_time`).

`score_state` and `player_counts` are **derived** from the event log, same as the roster (D16). The `trigger` values now have events that produce them — before D16, `red_card` and `half_time` were triggers nothing could emit.

### ShotValue
The richest source of genuine insight is accumulated shot quality diverging from the scoreline, which the score actively hides.

`event_id`, `value` (0–1, **hand-calibrated lookup, not a trained model**), `distance`, `angle` (kept so the number is explainable), `model_version`.

**Call this "shot quality" everywhere. Never xG.**

## C · Editorial output

Everything above this line is a faithful record. Everything below is a decision about what is worth saying, and to whom.

### Moment
Something the spotter judged worth saying. Roughly 30–60 per match out of ~1,800 events. The first opinionated layer — keeping it separate from the record is what lets the verifier check claims against untouched data.

`moment_id`, `clock_ms`, `type` (`goal` | `chance` | `tactical_shift` | `milestone` | `pattern`), `subject` (team or player), `importance`, `trigger_reading_ids`, `trigger_event_ids`, `epoch_id`, `model`, `model_version`.

### Claim
One structured, checkable assertion. **The explainer emits claims, not prose**; the sentence is generated downstream from them. Verifying a finished sentence means re-deriving its meaning, which is exactly the step that can go wrong.

| Attribute | Meaning |
|---|---|
| `claim_id`, `moment_id` | |
| `claim_type` | `descriptive` (a fact from events) \| `comparative` (a computed comparison) \| `interpretive` (a judgment). **Only interpretive claims require a backing signal reading** |
| `subject`, `metric` | What is asserted, e.g. `final_third_entries` |
| `value`, `comparison` | The asserted number and what it is measured against |
| `window` | The time range covered. Without it a number is unverifiable |
| `evidence_ids` | Event, run or reading IDs. **A claim with no citable evidence is dropped** |
| `model`, `model_version` | |

### Verification
The record of checking one claim. Keeping the verdict *and its reasoning* as data is what lets the producer view show a rejected claim with its reason — the clearest evidence of genuine multi-agent collaboration in the whole build.

| Attribute | Meaning |
|---|---|
| `verification_id`, `claim_id` | |
| `verdict` | `pass` \| `fail` |
| `checks` | Per-check results: **citation exists**, **temporal** (nothing cited from after the clock), **entity** (player was on the pitch), **value** (recomputed and compared), **entailment**, **narration coverage** |
| `recomputed_value` | What the system calculated independently. Catches wrong numbers, the most common failure |
| `failure_reason` | Readable |
| `latency_ms` | Live play has a budget |

### Rendition
One moment as one lens presents it. **The most important entity for the whole product thesis.** Storing a single rendered text on the `Moment` would architecturally throw away the personalization.

| Attribute | Meaning |
|---|---|
| `rendition_id`, `moment_id`, `lens_id`, `language` | |
| `headline`, `body` | What the viewer sees |
| `surviving_claim_ids` | Which claims this lens kept. **Each rendition is verified against its own surviving set**, not the moment's full set |
| `suppressed` | True when this lens deliberately shows nothing. **A populated record of silence** — this is what proves the lenses are independent |
| `suppression_reason` | `SuppressionReason`. **Required iff `suppressed` is true, null otherwise.** Exactly one value, resolved by the evaluation order below |
| `rendered_at` | For latency measurement |

#### Why `suppression_reason` exists

`Moment → Rendition` is exactly N, so roughly 120 of ~180 renditions per match are suppressed. Without a reason, the producer view and the post-match report can say *that* a lens stayed quiet but not *why*, and answering "why did the casual lens not show this" would mean re-running the pipeline.

**The split that matters:** `claims_filtered_out` and `verification_failed` have the same shape — no claims survived — but opposite meanings. The first is the product working correctly (the casual lens drops comparative claims by design). The second is a quality alarm (the explainer is producing claims that do not hold). Collapsing them into one value would make a failing system indistinguishable from a working one in the post-match report.

#### Evaluation order — first match wins

A single value, not a list, so the reason is deterministic. Without a declared order the same moment can yield different reasons on different runs and the audit is worthless.

| # | Reason | Meaning |
|---|---|---|
| 1 | `out_of_scope` | The moment's subject is not this lens's subject. It was never a candidate. |
| 2 | `muted` | The producer circuit breaker is active for this lens at this clock. |
| 3 | `degraded` | The system was below L1 and could not render at all. |
| 4 | `verification_failed` | Every claim for this moment failed verification. ⚠️ **A quality alarm.** |
| 5 | `claims_filtered_out` | No claim survived this lens's `allowed_claim_types` or depth filter. Correct behaviour. |
| 6 | `below_threshold` | `moment.importance` is below this lens's `importance_threshold`. |
| 7 | `rate_limited` | Important enough, but it would exceed `max_cards_per_10min`. |

The hierarchy reads: *was it ever a candidate → can we say anything → should we say anything → should we say it now.*

Positions 1 and 2 are the one arguable pair. Scope is first here because out-of-scope means structurally irrelevant, and reporting it as `muted` would inflate the apparent impact of a mute. Flip them if the producer view would rather see mute dominate.

### Recap — T3, may not be built
`recap_id`, `match_id`, `lens_id`, `length_variant`, `body`, `moment_ids`.

## D · Delivery and configuration

### Lens
The configuration of one viewing experience, as a point on two axes rather than a one-off preset. **Holding thresholds as data means adding a lens is inserting a row.**

| Attribute | Meaning |
|---|---|
| `lens_id`, `name`, `audience` | |
| `scope` | `match` \| `team` \| `player`. **Two different mechanisms — see D2.** `match` applies no subject logic. `team` keeps nearly every moment but reweights importance toward the chosen side and reframes to consequence-for-us. `player` is a hard filter |
| `breakthrough_types` | Moment types bypassing the scope filter. **Goals only.** Data, not a hardcoded check. A breakthrough moment is still rendered *through* the lens, not around it. Load-bearing only for `player` scope |
| `depth` | `casual` \| `engaged` \| `analyst` |
| `importance_threshold` | How important a moment must be for this lens. **The casual lens sets this high, so it may show nothing where the analyst lens fires** |
| `max_cards_per_10min` | Rate limit |
| `allowed_claim_types` | e.g. the casual lens drops comparative claims with raw numbers |
| `detail_level`, `language` | |
| `focus_team` | Which side this lens speaks for. Meaningful only when scope is `team` |
| `focus_player` | Meaningful only when scope is `player`. **Unused in v1** |

**The three shipping presets:** `match`×`casual`, `match`×`analyst`, `team`×`engaged`.

### ViewerSession
One person watching. A viewer here is a **session holding preferences, not a user account** — accounts are out of scope, so there is deliberately no user entity.

| Attribute | Meaning |
|---|---|
| `session_id`, `lens_id`, `language`, `joined_at` | |
| `focus_team` | The side they follow, if on the team lens. Required for that lens |
| `focus_player` | Unused in v1 |
| `last_seen_clock` | So a rejoin does not replay old cards |
| `stream_offset_ms` | How far this viewer's video lags the action. **Without this the product is the thing that spoils football.** See D7 |

### ProducerAction
A producer is a role, not an entity — what gets stored is what they did.

`action_id`, `target_id`, `action` (`suppress` | `hold` | `release` | `pin`), `actor`, `clock_ms`, `reason`.

### OverlayPacket
A rendition formatted for a graphics system. The fast path that does not wait for an LLM — what makes the output broadcast-ready rather than just a web page.

`packet_id`, `rendition_id`, `display_at_clock` (**match clock, never wall clock**), `duration_ms`, `template` (`lower_third` | `stat_bar` | `team_card` — `player_card` arrives with player scope), `payload`.

## E · Reference data

Computed once offline, not per match.

### SignalPrior
Solves the cold start. At four minutes there is no match baseline, and a z-score against five minutes of data is noise — exactly when a naive system floods the viewer with "unusual!" moments.

`signal`, `mean`, `stddev`, `sample_size`, `generator_version`. **A prior is only valid for the generator that made it.**

### MatchArchetype
Signals must be checked against several archetypes, or the simulator and the signals quietly co-adapt until the signals only work on the matches the generator happens to make.

`archetype_id`, `name` (comeback, one-sided, tight contest, scrappy), `parameters`.

### LexiconEntry — T3, may not be built
`term`, `language`, `lens`, `phrasing`.

## Enumerated types

Every closed set in the model, named. **Closed sets are enums, not strings** — the verifier's checks and the personalizer's dispatch both depend on these being exact, and a typo in a string field fails silently.

### Not enums

- **`language`** — an ISO 639-1 code as a plain string, not an enum. Only two ship, but hardcoding the pair into a type means adding a third language is a code change rather than a row.
- **`model`, `model_version`, `generator_version`** — free strings. They record what *did* run, which includes versions that did not exist when the enum was written.

### Degradation levels

`L0`–`L4` are a runtime concept from the degradation ladder, not an attribute on any entity today. `Rendition.suppression_reason = degraded` records that the ladder fell below L1. If you later want to know *which* rung produced a rendition, that is a new field and therefore a decision — raise it rather than adding it.

## Storage tiers

Volumes differ by orders of magnitude, so storage should too.

| Tier | Entities | Per match | Where |
|---|---|---|---|
| Hot, high volume | `Frame` | ~10,800 at 2 Hz (~54,000 at 10 Hz — rate still open) | **In-memory buffer**, optionally a compressed blob per match. Never a row per frame |
| Warm | `Event`, `Possession`, `SignalReading` | ~2,500 | Database, indexed by clock |
| Small and valuable | `Moment`, `Claim`, `Verification`, `Rendition` | ~200 | Database, keep indefinitely |
| Configuration | `Lens`, `SignalPrior`, `MatchArchetype` | tens | Database or files |

## Rules that make verification possible

- **Append-only.** Nothing in A or B is edited after emission.
- **Everything has an ID.** A claim with no citable ID cannot be verified.
- **Every derived object cites its inputs.**
- **The log can be frozen at any clock.** A view limited to events before the current time is the only thing the explainer ever sees.
- **Model and version travel with every AI-produced record.**
